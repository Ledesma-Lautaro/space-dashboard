<objective>
Prove the entire Phase 1 architecture end-to-end on one thin path: VT323 loads through `next/font`,
semantic tokens cascade from `:root` into a scoped CSS Module, one terminal `Panel` renders with
character-grid-aligned ASCII chrome, a single fixed overlay carries the CRT treatment, and a visible
control changes that treatment and persists the choice for the session.

advance, whether ASCII chrome aligns against a CSS-bordered box, whether scoped stylesheets read
`:root` custom properties under the default bundler, whether a browser-only preference read survives
hydration — is exercised here on the executor's best early-context tokens. Every later plan in this
phase widens this slice rather than discovering an architectural dead end after ten committed layers.

This is production code, not a prototype. Nothing written here is thrown away; the expansion plans
add tiers, fixtures, components and breakpoints on top of exactly these files.

Output: a running single-screen dashboard shell with one populated terminal panel and a working CRT
intensity control.

<planner_assumptions>
Two points are load-bearing for this plan and are stated here explicitly rather than left for the
executor to rediscover. Neither contradicts a locked decision; both resolve an internal inconsistency
between two approved documents.

**A. ASCII chrome renders at Body size, not Heading size.** `01-UI-SPEC.md` §Typography assigns
Panel title-bar text a 24px Heading size, while §ASCII Border Contract requires the top border row —
which contains that title — to align on the same character grid as the panel body. `1ch` resolves per
element font-size, so a 24px title inside a 20px-grid row lands at a 9.6px advance against an 8px
grid and the row cannot align. Resolution: the ASCII border rows and the title inside them render at
Body size (20px / 28px line-height); title emphasis comes from `--color-nominal-bright`, which is
exactly the mechanism §Typography already prescribes for a single-weight face. The 24px Heading token
stays declared and is used for headings that sit outside ASCII chrome.

**B. The truncation ellipsis is not exercised in Phase 1.** `01-UI-SPEC.md` specifies a single `…`
(U+2026) as the truncation character. That codepoint falls inside a unicode-range VT323's served
subsets declare, but glyph presence was not independently confirmed by the research's cmap
inspection. No Phase 1 panel title comes close to the truncation cap, so this is zero-risk now.
Implement `…` as specified; plan 01-03 carries the glyph confirmation and the documented fallback
(a single ASCII `.`) if the ellipsis renders from a fallback font.
</planner_assumptions>

  <action>
    The stored preference is the only input this phase reads that a user can edit out from under it —
    it is same-origin editable through DevTools and it can be missing, malformed, or impossible to
    write at all. Make every one of those cases a defined behaviour rather than an exception that
    reaches React.

    Harden `readCrtLevel` so it wraps the storage read in a try/catch, validates the returned string
    against the `CRT_LEVELS` tuple by membership, and returns the module's in-memory value for
    anything that is not an exact member — including a null, an empty string, a differently-cased
    variant, and an arbitrary attacker-supplied string. Validation is membership against the fixed
    enum, not a cast and not a truthiness check; a cast would let any string through into the
    intensity calculation.

    Harden `writeCrtLevel` so it assigns the in-memory value BEFORE attempting the storage write and
    swallows a throw from the write. Order matters: this is what keeps the control working for the
    rest of the session in a browser where site data is blocked or the private-mode quota is zero. Add
    a short comment above the catch naming the concrete condition it exists for so a future reader
    does not delete it as dead code.

    Harden `crtIntensityValue` so an out-of-enum argument returns the full-intensity default rather
    than `undefined`, which would otherwise land in the custom property as an invalid value and leave
    the overlay in an undefined visual state.

    In `CrtControl`, guard the effect that writes the custom property so a level outside the enum can
    never reach `setProperty`. Keep all storage access inside the pure module — the component must not
    reference the storage API directly, so the whole failure surface stays in one testable place for
    the Phase 3 runner to pick up.

    Finally, add a `## Verifying the storage failure path` section to the plan summary you write at
    the end, spelling out the exact DevTools procedure: override the storage prototype's setter to
    throw, then cycle the control and confirm it still changes the overlay and that no uncaught error
    appears in the console.
