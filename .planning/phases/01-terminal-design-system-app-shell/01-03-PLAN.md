<objective>
Turn the tracer's single-width panel into the full ASCII Border Contract: three character-count tiers
derived from the font's real advance, a deterministic title-truncation formula, an eight-row body cap
with internal scroll, and a clean degrade below the compact tier where the ASCII rows are replaced by
plain CSS borders.

Purpose: this is the phase's highest-risk area, named as such in the phase context — ASCII chrome and
fluid responsive layout genuinely fight each other, and the mitigation is a fixed character-step
scale plus an explicit degrade threshold, not "handle it responsively". The tracer proved the
mechanism at one width; this plan makes it hold at every width the dashboard will actually be viewed
at, and gives Phases 4, 5 and 10 a panel they can opt into a wider tier from without inventing
markup.

Output: a `Panel` that any later phase can drop content into at any of three widths, plus a
documented fallback below the narrowest one.
</objective>

    Split the row construction into two exported pure functions so both are readable and, when Phase 3
    brings a test runner, directly testable without rendering anything. `buildBorderRow` takes a title
    and a tier and returns the top row; `buildBottomRow` takes a tier and returns the bottom row. Both
    must return a string whose length is exactly the tier's character count — assert that invariant
    inside the functions in development rather than trusting it, because a one-character drift is
    exactly the failure this whole mechanism exists to prevent and it is invisible until someone looks
    closely at a rendered corner.

    The top row is: a plus, two hyphens, a space, the title, a space, two hyphens, a pad run of
    hyphens, a closing plus. The pad length is the tier character count minus the chrome constant minus
    the title length. The bottom row is a plus, a pad run spanning the tier count minus two, and a
    closing plus.

    `truncateTitle` caps the title at the tier character count minus the chrome constant. Over that
    cap, cut to one character less than the cap and append the horizontal-ellipsis character the
    UI-SPEC specifies. Confirm during this task's human-check that the ellipsis renders in the terminal
    face rather than dropping to a fallback; if it falls back, replace it with a single ASCII period
    and record the substitution in the summary. No Phase 1 panel title approaches the cap, so this
    costs nothing now and removes a latent trap for the Phase 4 and 5 titles that carry a live count.

    Cap the visible body at eight rows using the body line-height token, then switch to internal
    vertical auto-scroll. The height is fixed, not max-height driven by content: the two border rows
    must not move as content is added, which is the point of the cap. Style the scrollbar minimally in
    the dim chrome colour so it reads as part of the terminal rather than as an OS artifact, and make
    sure the scroll container keeps its `2ch` horizontal padding so rows stay on the character grid
    even when a scrollbar takes width — use `scrollbar-gutter: stable` so the grid does not shift the
    moment content overflows.

    Add a short comment block at the top of `Panel.tsx` naming the two invariants a future editor must
    not break: every constructed row is exactly the tier's character count long, and only the three
    structural ASCII characters appear in a row. Do not restate the glyph set as a list of forbidden
    codepoints in the comment — name the allowed ones.

  <action>
    There is a width below which even the narrowest tier cannot hold its character grid — a very
    narrow phone viewport once safe-area padding is subtracted. Below that width the ASCII rows must
    disappear entirely rather than misalign, because a half-character overhang reads as a bug while a
    plain rule reads as a deliberate style.

    Declare the panels region in the shell stylesheet as an inline-size query container so the panel
    can respond to the space it is actually given rather than to the viewport, which keeps the degrade
    correct when Phase 10 puts a panel inside a narrower HUD column. Give the container an explicit
    name so an unrelated ancestor container cannot capture the query by accident.

    In the panel stylesheet, add a container query that fires when the container's inline size is below
    the compact tier's width. Inside it: hide both ASCII rows, apply `border-top` and `border-bottom`
    in the dim chrome colour to the panel body so the box still reads as a bounded region, and reveal
    the title as plain text above the top border at body size in the bright nominal colour. Keep the
    left and right CSS borders — they were never character-based and they align at any width.

    Render the plain-text title in the markup unconditionally and let CSS decide which of the two title
    presentations is visible, rather than branching in JavaScript on a measured width. A JavaScript
    width branch would need a resize observer and would render the wrong variant on the server pass;
    CSS resolves it with no hydration surface at all. Make sure only one of the two is exposed to
    assistive technology at a time so the title is not announced twice — hide the decorative ASCII rows
    from the accessibility tree entirely, since a row of hyphens carries no meaning to a screen reader.

    Set the panel's own width to the smaller of its tier width and 100% of the container so a compact
    panel in a narrower container shrinks rather than overflowing horizontally.
  </action>
