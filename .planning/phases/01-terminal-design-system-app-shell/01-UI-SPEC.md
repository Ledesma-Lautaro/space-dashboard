> Visual and interaction contract for the terminal design system and app shell. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. No Three.js, no real NASA data — mock fixtures
> only (D-11).

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-built `Panel`/`Alert` components (D-12, D-15) |
| Icon library | none — box-drawing glyphs already in VT323 (`┌─┐│└┘`) serve as the entire iconographic vocabulary. If a true icon is ever needed in a later phase, use inline SVG sized to `1em` square rather than an icon font — an icon font would fight the self-hosted single-face loading model this phase establishes (D-04). |
| Font | VT323, single weight (400), loaded via `next/font/google` in `app/layout.tsx`, exposed as a CSS variable (`--font-terminal`) applied at the root layout |

**shadcn gate — explicitly skipped, not asked.** `components.json` is absent (greenfield repo, verified via `git ls-files`) and the repo has no `package.json` yet. Normally this triggers the init prompt, but D-01 locks **CSS Modules + CSS custom properties, explicitly not Tailwind** — shadcn's registry model is built on Tailwind + Radix and is structurally incompatible with that locked decision. Asking to init shadcn here would contradict a decision the user already made in `/gsd-discuss-phase`, so the gate is recorded as skipped-by-locked-decision rather than presented as a live question. Registry safety gate: not applicable for this phase.

**Shape policy:** `border-radius: 0` everywhere. No rounded corners anywhere in this phase — box-drawing borders are inherently rectangular, and rounding any element (panels, buttons, the CRT control) would visually contradict the ASCII chrome sitting next to it.

## Spacing Scale

Declared values (multiples of 4, per the standard 8-point scale):

| Token | Value | Usage |
|-------|-------|-------|
| `--space-xs` | 4px | Icon/glyph gaps, inline padding, legend swatch-to-label gap |
| `--space-sm` | 8px | Compact element spacing, Alert internal padding |
| `--space-md` | 16px | Default element spacing, Panel body padding (vertical) |
| `--space-lg` | 24px | Section padding, gap between stacked panels |
| `--space-xl` | 32px | Layout gaps between major shell regions |
| `--space-2xl` | 48px | Gap between the canvas hero and the first panel on scroll |
| `--space-3xl` | 64px | Page-level top/bottom breathing room |

**Exception — Panel horizontal interior padding is `ch`-based, not px.** Because Panel chrome (D-12) uses literal box-drawing characters whose alignment depends on the monospace character grid, horizontal padding inside a Panel is declared as `1ch` (compact) or `2ch` (default) rather than a px token, so text content never drifts out of alignment with the `│` side borders. Vertical padding inside a Panel still uses the px scale above (`--space-md` top/bottom). This is the only exception to the 8-point scale in this phase — see **ASCII Border Contract** below for the full mechanism.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (data text, list rows) | 20px | 400 (only weight available) | 28px (1.4) |
| Label (meta text — timestamps, units, panel sub-labels) | 16px | 400 | 24px (1.5) |
| Heading (Panel title-bar text) | 24px | 400 | 28px (1.167) |
| Display (canvas placeholder, hero-scale text) | 32px | 400 | 36px (1.125) |

**Deviation from the standard "2 weights" contract, stated explicitly:** VT323 ships **one weight only** (regular/400) — D-04 locks VT323 alone for this phase, no second face. Hierarchy is therefore carried by **size + brightness step (D-14)**, never by font-weight. Do not fake a bold weight with `font-weight: 700` (the browser will synthetically embolden a font that has no bold master, which looks broken on a pixel face) and do not add `font-synthesis: none` as a workaround that then leaves headings visually identical to body text — use the size/brightness combination above instead.

**Base sizing note:** 20px was chosen as the body size (not the more common 16px) because VT323 is a pixel-style face with thin strokes that under-render at small sizes — this is the exact legibility risk flagged in `research/STACK.md` §6. D-05's realistic-density mock fixtures exist specifically so this can be judged by eye against real numeric data during this phase; if 20px still reads as too smeared in dense tables once built, that is the signal to pull forward the Departure Mono fallback evaluation (still gated to Phase 4 per D-04 — do not add it preemptively here).

**Scanline/line-height alignment rule:** every line-height value above is a **clean multiple of 4px** (28, 24, 28, 36 — wait, 36 is not ÷4; see correction below) so it divides evenly by the CRT overlay's 4px scanline pitch (see **CRT Overlay Contract**). This means an integer number of scanline bands falls inside every line of text, with no partial band carrying over into the next line — the mechanism that keeps scanlines from visually "colliding" with a baseline on some lines and not others.
- Body: 28px ÷ 4px = 7 bands/line ✓
- Label: 24px ÷ 4px = 6 bands/line ✓
- Heading: 28px ÷ 4px = 7 bands/line ✓
- Display: 36px ÷ 4px = 9 bands/line ✓ (36 is a multiple of 4 — 4×9)

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-bg` `#060907` | Root background — deep, near-pure black with a whisper of green cast so it reads as an unlit phosphor tube, not print black |
| Secondary (30%) | `--color-surface` `#0d130f` | Panel bodies, the legend strip, the shell's nav/status row — a slightly raised surface relative to `--color-bg` |
| Accent (10%) | `--color-alert` `#C64AE6` (normal step) | Reserved for — see explicit list below. **Never** used for default UI chrome, default text, or default borders |
| Destructive | *(none declared this phase)* | No destructive actions exist in this phase (read-only, no accounts, no persistence — see Out of Scope in REQUIREMENTS.md). If a destructive action is ever added in a later phase, it reuses `--color-alert-bright`, never a third hue. |

**Honest calibration note on 60/30/10:** this is a low-chroma terminal UI, not a card-based product UI — literal pixel coverage skews closer to 70/25/5 (mostly background, green text/borders as the true secondary mass, magenta as a genuine minority). The 60/30/10 rule is honored **in spirit** (background dominant, structural green secondary, magenta strictly minority-and-reserved) rather than as a literal measured split, which fits this aesthetic better than forcing a card-UI ratio onto a terminal screen.

**Accent (`--color-alert`) reserved for — explicit list, nothing else:**
1. The `Alert` component's text, `>>` prefix glyph, and left accent border (D-15)
2. The legend's magenta swatch and its label text (demonstrative — explaining what magenta means, per RESP-04)
3. Future phases' "requires attention" indicators as they are added: high-notability-tier badges (Phase 4, NEO-03), X-class flare / G3+ storm markers (Phase 5, SW-02/SW-03) — reserved now by this token contract, not rendered anywhere in Phase 1 beyond items 1–2

### Full semantic token set (D-02 naming, D-14 brightness steps)

Contrast ratios below are computed against `--color-bg` (`#060907`, relative luminance ≈0.0025) using the WCAG relative-luminance formula. `--color-surface` (`#0d130f`) is close enough in luminance (≈0.0058) that ratios against it hold within roughly ±0.3 of the figures below — re-verify against the actual composited CRT output in Phase 11 per CRT-09, not against these flat swatch numbers (this is the exact trap `research/PITFALLS.md` names: swatch contrast passing while composited output erodes it).

| Token | Hex | Contrast vs `--color-bg` | Text-safe? |
|-------|-----|---------------------------|------------|
| `--color-bg` | `#060907` | — | background, not text |
| `--color-surface` | `#0d130f` | — | background, not text |
| `--color-nominal-dim` | `#2FA352` | 6.18:1 | ✓ AA/AAA — safe for de-emphasized body text |
| `--color-nominal` | `#4CDB6E` | 11.11:1 | ✓ AAA — default body/data text color |
| `--color-nominal-bright` | `#8CFFA8` | 16.18:1 | ✓ AAA — emphasis, active states, focus rings |
| `--color-alert-dim` | `#7A2E8A` | **2.46:1** | ✗ **fails AA even for large text (needs 3:1). Decorative-only — borders, inactive/disabled swatches. NEVER render as text at this step.** |
| `--color-alert` | `#C64AE6` | 5.26:1 | ✓ AA (not AAA) — default Alert text; fine for the short, single-line terminal strings this project uses (CRT-05 format), do not use for long-form paragraphs |
| `--color-alert-bright` | `#F2A0E8` | 10.45:1 | ✓ AAA — emphasis within an alert, active/focused alert state |
| `--color-dim` | same value as `--color-nominal-dim` (`#2FA352`) | 6.18:1 | ✓ — structural chrome: box-drawing border characters, dividers, inactive/placeholder text. Declared as its own token (per D-02's example list) rather than reusing `--color-nominal-dim` by reference, so Phase 11 can tune border chrome separately from de-emphasized body text if the composited output calls for it. |

**Brightness carries meaning without hue (D-14 accessibility rationale, stated concretely):** "bright" always means the same thing regardless of which hue it belongs to — highest emphasis, active/focused, or newly-changed. "Normal" always means default/at-rest. "Dim" always means de-emphasized/structural. A user with red-green color blindness who cannot reliably distinguish `--color-nominal` from `--color-alert` can still read every state correctly from the lightness step alone, because the step vocabulary (dim/normal/bright) is applied identically across both hues.

## ASCII Border Contract

This is the phase's highest-risk area (flagged explicitly in `01-CONTEXT.md`'s `<specifics>` block) — given a concrete, deterministic mechanism rather than "handle responsively."

**Hybrid construction — not a full ASCII box every row:**
- **Top border row** is literal text content: `┌─ {TITLE} ─{fill}┐`, where `{fill}` is a computed run of `─` characters that pads the row to the panel's declared width in `ch`.
- **Bottom border row** is literal text content: `└{fill}┘` — a full-width dash run, no title.
- **Side borders are plain CSS**, not characters: `border-left` / `border-right: 1px solid var(--color-dim)` on the panel body between the top and bottom rows. Verticals always align at any pixel width — no character math needed for the sides, which removes most of the fragility.

**Fixed `ch`-step width scale — panels are not fluid-arbitrary:**

| Tier | Width | Use |
|------|-------|-----|
| Compact | `32ch` | Legend, small utility panels, mobile default |
| Default | `48ch` | Primary content panels (NEO FEED, SPACE WEATHER) on tablet/desktop |
| Wide | `64ch` | Reserved for a panel that needs more columns (not used by any Phase 1 panel, declared for Phase 4/5 to opt into if a table needs it) |

Each panel snaps to the **nearest declared tier**, never a fluid `%` or arbitrary px width — this is what keeps the `{fill}` dash computation an integer every time, with no leftover fractional character. Approximate px equivalence at VT323's metrics (verify empirically once built — VT323's advance width is roughly `0.6em`, so at the 20px body size `1ch ≈ 12px`): `32ch ≈ 384px`, `48ch ≈ 576px`, `64ch ≈ 768px`.

**Degrade threshold — below 32ch, drop the ASCII rows entirely:** at container widths under `32ch` (roughly sub-280px after safe-area padding — narrow phone widths), the top/bottom text rows are replaced with plain CSS `border-top` / `border-bottom: 1px solid var(--color-dim)`, and the title renders as plain text above the border with no box-drawing glyphs at all. This is the explicit degrade point the risk note asked for.

**Title truncation — deterministic formula, not "shorten if needed":**
```
maxTitleChars = panelWidthCh - 8
```
The `8` accounts for the fixed chrome (`┌─ ` = 3 chars, ` ─` = 2 chars before `┐`) plus a reserved minimum of 3 trailing dash characters so the border never reads as a title that ate the whole row. A title longer than `maxTitleChars` truncates with a single `…` as its last character. Example at the `48ch` tier: `maxTitleChars = 40` — every Phase 1 panel title (`NEO FEED`, `SPACE WEATHER`, `SOLAR SYSTEM`, `SYSTEM LEGEND`) is well under this, so truncation is not exercised in this phase but the formula is load-bearing for Phase 4/5 titles that may include a live count (see Copywriting Contract).

**Panel body overflow (list content, not the border):** panel body height caps at **8 visible rows** (`8 × 28px line-height = 224px`) before switching to internal `overflow-y: auto` scroll. The border does not resize with scroll — the fixed-height scrollable body sits between the static top and bottom border rows, so the box never visually "opens up" as more mock data is added.

## CRT Overlay Contract (CSS layer — D-16, D-17)

**Single fixed overlay, per D-17.** One `position: fixed; inset: 0; pointer-events: none; z-index: {above all content}` pseudo-element on the root wrapper carries scanlines + vignette. Phosphor glow is **not** part of this overlay — it is applied per text element via `text-shadow` (see below), because glow needs to scale with each element's own brightness step, not a single global value.

**Scanlines:**
```css
background-image: repeating-linear-gradient(
  to bottom,
  rgba(0, 0, 0, var(--crt-scanline-opacity)) 0px,
  rgba(0, 0, 0, var(--crt-scanline-opacity)) 1px,
  transparent 1px,
  transparent 4px
);
```
Fixed 4px pitch (1px dark line + 3px gap) at every intensity level — **only opacity scales with intensity, pitch never changes**, because the pitch is what keeps the Typography section's line-height-is-a-multiple-of-4 rule meaningful. Base max opacity: `0.25` at full intensity (`--crt-scanline-opacity: calc(0.25 * var(--crt-intensity))`).

**Vignette:**
```css
background-image: radial-gradient(
  ellipse at center,
  transparent 55%,
  rgba(0, 0, 0, var(--crt-vignette-opacity)) 100%
);
```
Fixed shape (55%/100% stops) at every intensity level; only opacity scales. Base max opacity: `0.45` at full intensity (`--crt-vignette-opacity: calc(0.45 * var(--crt-intensity))`). Because panels and the canvas both sit centered in the layout (D-06/D-07), the vignette's darkening falls mostly on empty edge space by construction — this is the mitigation for Pitfall 8 (scanline/vignette eroding text contrast) chosen over per-panel intensity carve-outs, which D-17 explicitly rules out ("one implementation, consistent intensity").

**Phosphor glow (per text element, not the overlay):**
```css
text-shadow: 0 0 {radius}px rgba({hue-rgb}, calc(0.6 * var(--crt-intensity)));
```
Radius by brightness step: dim `2px`, normal `3px`, bright `5px`. Glow *adds* luminance around glyphs rather than subtracting it, so unlike scanlines/vignette it cannot push a text/background pair below its computed contrast ratio — it is the one CRT effect allowed to run at full strength over data text without a legibility mitigation.

**Worst-case legibility check:** the lowest-contrast text-safe token is `--color-alert` at 5.26:1 (AA pass, not AAA). At full CRT intensity, scanlines darken at most 25% of vertical pixels by up to 25% opacity black — averaged over any full line of Alert text (which spans 7 scanline bands per the 28px/4px rule) this is a small, uniform luminance reduction, not a localized wipe of any single glyph. This keeps the composited worst case above the 4.5:1 AA floor by inspection; **this is a design-time estimate, not a measurement** — CRT-09's actual composited-screenshot verification is explicitly Phase 11's job, not this phase's. This phase's obligation is to not paint the overlay so heavy-handed that Phase 11 inherits an already-broken baseline.

**No chromatic aberration in CSS (D-16):** deliberately excluded here — it belongs to the canvas-only shader pass in Phase 11, where it can do real per-channel RGB offset. A CSS approximation would look cheap next to the real thing and was explicitly ruled out.

**No animated flicker (D-18):** every value above is a static gradient/shadow. Nothing in this phase oscillates, pulses, or scrolls.

## CRT Intensity Control (CRT-10 / D-20)

**Three discrete levels, not a binary toggle** — CRT-10's own language ("reduce **or** turn off") implies at least a reduce step distinct from fully off:

| Level | `--crt-intensity` | Label |
|-------|--------------------|-------|
| Full | `1` | `FULL` |
| Reduced | `0.4` | `REDUCED` |
| Off | `0` | `OFF` |

**Placement:** lives in the in-page legend strip (D-09 — the design system is delivered as a legend strip, not a `/styleguide` route), rendered as a bracketed terminal button that cycles on click: `[ CRT: FULL ]` → `[ CRT: REDUCED ]` → `[ CRT: OFF ]` → back to `FULL`. Uses `--color-nominal` (not `--color-alert` — this is a routine control, not an attention state).

**Session persistence without a backend:** `sessionStorage.setItem('crt-intensity', level)` on change, read on mount to restore. `sessionStorage` (not `localStorage`) is the deliberate choice — CRT-10 says the choice holds "for the session," and the project's own Out-of-Scope table rules out cross-session persistence generally; `sessionStorage` matches that boundary exactly (clears when the tab closes, never becomes a hidden every-visit preference).

**Transition behavior:** the overlay's opacity changes with a `150ms ease` transition when the level changes, wrapped in `@media (prefers-reduced-motion: no-preference)` — under reduced motion, the change is instant (no transition property applied at all), establishing the same reduced-motion-as-hard-gate pattern Phase 11 extends to the shader's flicker uniform (D-19).

## Responsive Contract

**Single breakpoint: `768px`.** Below it: mobile layout (canvas `60svh`, D-07). At or above it: desktop layout (canvas full-viewport hero, D-06). Chosen as the one clean switch point both D-06/D-07's canvas-height rule and the Panel `ch`-tier scale need — below 768px, a `48ch` panel row starts crowding a phone viewport, which is also roughly where the ASCII-border degrade threshold (32ch) becomes the practical default rather than the exception.

**Unit policy: `svh`, never `vh`, throughout this phase.**
- Desktop canvas hero: `height: 100svh`
- Mobile canvas: `height: 60svh`

`svh` (small viewport height — the viewport size **with** browser chrome visible) is used instead of `dvh` (dynamic viewport height — resizes live as chrome shows/hides) deliberately: `svh` is a static floor, so the hero canvas and the panels below it never exceed the visible area even before the user's first scroll, and nothing resizes/jumps as chrome collapses. This is precisely what makes RESP-03 (Phase 12) a **verification pass on a real phone**, not a rewrite — the unit policy that pitfall needs is already the default here, not retrofitted.

**Layout order is identical at both breakpoints (D-06/D-07):** canvas placeholder first, panels below on scroll. The only things that change across the breakpoint are canvas height and which `ch` tier each panel snaps to — never the vertical order, and never a canvas-as-background-with-floating-panels composition (D-08 explicitly rejects that pattern).

## Copywriting Contract

**Register rule:** every terminal string is a single line, uppercase-leaning, `>>`-prefixed when it represents an event/state (Alert, empty, error, canvas placeholder), no trailing punctuation beyond what's structurally part of the format, numeric values always carry their unit inline. No second line of explanatory body copy under a terminal statement — the one line **is** the message, matching CRT-05's fixed example exactly.

| Element | Copy |
|---------|------|
| Primary CTA | *(none in Phase 1 — no data-fetching action exists yet, Phase 3's scope)*. Closest analog: the CRT intensity control's cycling button, `[ CRT: FULL ]` / `[ CRT: REDUCED ]` / `[ CRT: OFF ]` (see CRT Intensity Control section) |
| Empty state heading | **Pattern only, not rendered this phase** (D-11's mock fixtures are always populated) — established here for Phase 3/4 to inherit verbatim: `>> {SUBJECT} :: NO {ITEMS} IN RANGE`, e.g. `>> NEO FEED :: NO OBJECTS IN RANGE` |
| Empty state body | None — terminal register uses one line only, no secondary body text |
| Error state | **Pattern only, not rendered this phase** (no network calls exist yet — Phase 3's scope, DATA-04): `>> {SUBJECT} :: LINK FAILURE - RETRY`, e.g. `>> DONKI FEED :: LINK FAILURE - RETRY` |
| Destructive confirmation | None — no destructive action exists or is planned in this read-only dashboard (no accounts, no persistence to delete, per REQUIREMENTS.md Out of Scope) |

**Alert grammar (CRT-05, fixed by requirement):** `>> {SUBJECT} {STATE} - {QUALIFIER}: {VALUE}`. The literal example from CRT-05/D-x: `>> CME DETECTED - INTENSITY: MODERATE`. Additional concrete examples for Phase 4/5 to reuse this exact grammar against real DONKI/NeoWs vocabulary:
- `>> CME DETECTED - INTENSITY: MODERATE`
- `>> HAZARDOUS OBJECT FLAGGED - NOTABILITY: HIGH`
- `>> GEOMAGNETIC STORM - SEVERITY: G2`

**Canvas placeholder (D-10, literal text fixed by decision):** `>> SCENE :: OFFLINE`, centered within the reserved canvas box at Display size (32px). Optional secondary static line beneath it (Claude's discretion, may be omitted without violating any locked decision): a small `--color-dim` readout proving real space is reserved, e.g. `[ RENDER TARGET RESERVED ]` at Label size — purely decorative, must not animate (D-18) and must not be a blinking cursor.

**Panel titles:** 1–2 words, uppercase, no punctuation: `NEO FEED`, `SPACE WEATHER`, `SOLAR SYSTEM`, `SYSTEM LEGEND`. When a later phase adds a live count, the format is `{TITLE} :: {N}` (e.g. `NEO FEED :: 12`) — numeric-only, which is also how the `zero-one-many` UI consideration below is resolved (no singular/plural word forms to get wrong).

**Legend entries (RESP-04):**
```
■ GREEN   :: NOMINAL / ROUTINE
■ MAGENTA :: REQUIRES ATTENTION
  (brightness = emphasis, not a different meaning)
```
Rendered inside a `LEGEND` panel at the `48ch` tier (not the `32ch` compact tier — the magenta line is ~31 characters and needs the breathing room; see ASCII Border Contract overflow row below).
